# Explicit Finish acceptance

QUILS-36 adds an internal `SignerFinish` acceptance transaction. It has no public endpoint or UI and does not itself mark the signer Signed or seal the PDF. A durable acceptance with `ProcessedAt` unset represents pending checkpoint publication. QUILS-37 atomically queues its supported [checkpoint worker](signer-checkpoints.md), which verifies/publishes the accepted exact PDF, records `signer_completed`, and only then advances signing.

The caller must provide affirmative Finish intent and the exact version of `SignerFinishStatement`, together with the protected immutable review receipt and isolated signer session. The statement text and SHA-256 are stored in the immutable acceptance and audit evidence. Client values, marks, object references, identities and signing timestamps are never Finish inputs.

The transaction takes the common envelope lock and verifies live session/nonce/request scope, consent and sequential eligibility, current owned saved-field revisions, required entries, adopted asset hashes/evidence, review preparation evidence, and complete candidate PDF length/hash. The original source PDF is independently re-read and verified before acceptance. The server chooses the actual Finish instant after storage verification. Its UTC date must match the review candidate's prospective Date Signed, and the receipt/session/envelope must remain live through the final checks.

Acceptance atomically consumes the review candidate, fills owned Date Signed fields from that actual server UTC date/time, saves one immutable signer-owned acceptance and final owned-field snapshot, and appends `signer_finish_accepted`. The record preserves source/candidate/adoption/disclosure/session/snapshot/recipe hashes, exact candidate object/length/hash, statement text/version/hash, review preparation/expiry, actual Finish time and final field values/revisions/hash. Other fields and source/candidate PDF bytes remain unchanged. This event records explicit intent against the exact reviewed copy; it explicitly identifies checkpoint publication as pending.

The PDF is not rerendered after acceptance. Its recipe contains the review preparation context, while the acceptance separately records actual Finish time. Date-only rendering remains exact because acceptance requires the same UTC date. A review that crosses midnight before acceptance must be prepared and reviewed again. Completion certificates must use actual accepted Finish times, never review preparation times.

An accepted signer cannot edit/clear fields, prepare or adopt/replace marks, obtain a new review, decline, or redeem/dispatch a fresh invitation. Existing public reads also stop using editable signing context. The future processing/confirmation page must use its own narrow authorized read path; the acceptance bypass is internal and cannot grant edit access.

Concurrent exact retries return one durable acceptance and audit event. A previously accepted receipt can confirm that same acceptance after review expiry or UTC rollover while its original isolated session remains live; it cannot accept a new action. Replay checks the exact receipt/candidate/session, immutable acceptance, both preparation and acceptance evidence, and stored PDF bytes. An older/different review or another nonce cannot claim it. Expired sessions, changed evidence, fields snapshots or candidate bytes fail closed.

Storage, validation, hint or audit failure before commit rolls back Date Signed, receipt consumption, acceptance and checkpoint work, leaving entries editable and review retryable. Lost commit acknowledgment is recovered by the accepted-receipt path without creating another acceptance or deleting candidate bytes. Finish writes a durable wake hint; it performs no document blob writes because the reviewed immutable PDF already exists.

EF and SQL constraints enforce signer/candidate ownership, one acceptance per signer and candidate, valid Finish/review date/time bounds and bounded JSON/hash/PDF metadata. EF rejects acceptance-content changes; runtime SQL updates are restricted to publication time and the next invitation ID. Privileged retention must first clear the envelope current-copy reference/version, delete Finish acceptances before review candidates, then candidates and fields before signature previews/signers/envelope, and purge all envelope objects/work. No retention policy, background polling or cloud changes are introduced.

SQL Server/Azurite tests cover explicit intent/version, concurrent/idempotent acceptance, required/current snapshot and nonce/scope checks, actual Date Signed, UTC rollover and storage-crossed expiry, corrupt source/candidate/assets, post-acceptance freezing, fresh-link denial, rollback/lost commit recovery, exact replay evidence and immutable database ownership/retention ordering. Public review/Finish/confirmation, final completion and sender confirmation remain separate work.

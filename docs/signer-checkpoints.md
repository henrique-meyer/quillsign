# Accepted checkpoints and sequential current copies

QUILS-37 implements durable publication of accepted signer reviews. Internal Finish acceptance now atomically creates one supported Rendering work item and a durable storage wake hint. Queue publication happens after commit and can recover from the hint. Empty queues do not open SQL; there is no new background SQL polling. Public review/Finish/confirmation screens and final completion remain separate work.

The checkpoint worker takes the envelope lock before the work lock and verifies its exact payload, lease owner/attempt/deadline, current sequential source and immutable acceptance/candidate/field/adoption/disclosure bindings. It verifies preparation, adoption and Finish evidence, canonical saved mark assets, and complete bounded source/candidate PDF lengths and hashes. Short-lived in-process capabilities permit only an exact accepted source/candidate/asset object read. Worker verification remains possible after the original signer session or preview expires, without manufacturing a signer identity or broadening cookie authority.

The accepted review PDF becomes the checkpoint **byte for byte**. Rendering happened before explicit Finish; the worker does not rerender an unreviewed variant. Under the same transaction it records the versioned envelope current-copy reference, marks the signer Signed with actual accepted Finish time/IP/user agent, sets publication time and the once-only next invitation ID, and appends `signer_completed` with `checkpoint_sha256` plus source/review/acceptance/snapshot/recipe provenance. Original `SentPdfBlob`/`SentPdfSha256` and their bytes remain immutable.

Current-copy resolution verifies a contiguous prefix of Signed signers, each owned processed acceptance/candidate and its source/hash linkage, preparation/Finish/publication evidence, actual Signed time and the envelope's current reference/version. An earlier Signed signer with a missing or inconsistent checkpoint cannot fall back to the original sent PDF. Later invitation, PDF consent, capture/adoption, field and review contexts use the verified current copy; older source-bound sessions cannot become a later signer's context.

Next invitation outbox/work records are prepared in the checkpoint publication transaction, with wake publication after commit. Both the protected invitation payload and the token created at actual dispatch bind the exact current document object/hash and disclosure hash. Redemption compares all three before consuming the token. Old unbound invitation records remain stored for retention but cannot redeem; no existing token is silently rebound to another copy. Dispatch rejects stale payloads, suppressed recipients and unavailable source state before creating/submitting an invitation. A suppression does not erase the preceding accepted checkpoint; the failed next invitation requires subsequent sender/operator recovery.

Storage, integrity, audit, lease, disabled delivery or hint failures cannot partially publish Signed state or a next invitation. Known transactions roll back; unknown commit outcomes retain accepted bytes and recover the same publication. Durable work retries preserve existing backoff/attempt limits. Duplicate wakeups and recovery after later signer progress cannot republish a checkpoint or resend its next invitation. Generic failure codes contain no documents, tokens, values or private endpoints.

Accepted/completed confirmation and own-checkpoint reads require the original live isolated session, exact accepted protected proof, request/signer/nonce/source/disclosure binding, current chain and immutable evidence. Reads buffer and verify the whole PDF and recheck live authorization after storage. Pending acceptance can be confirmed; checkpoint download requires publication. A signer retains their own accepted checkpoint after later signers progress, while editable signing context stays closed. Review expiry alone does not erase accepted proof; session expiry or an ended envelope still denies reads. No ordinary signer cookie receives general blob access.

After the last signer, the current copy contains all accepted entries and the envelope remains Sent pending a later supported certificate/seal/final-delivery workflow. This slice does not claim envelope completion, create a sealing job without a handler, send live email or change operator policies.

The migration adds an envelope-owned current-acceptance reference/version, a unique next invitation ID and token source/disclosure binding. Runtime acceptance updates remain restricted to publication metadata. Privileged retention must first clear the envelope current reference/version, then delete Finish acceptances before review candidates, then candidates/fields before signature previews/signers/envelope, and purge all envelope objects and durable work/hints. No retention policy is introduced.

SQL Server/Azurite tests exercise two sequential signers through actual queue processing, invitation dispatch, redemption, consent, adoption, fields, reviews and checkpoint publication. They check exact bytes and prior contents, actual server dates, immutable original source, bound tokens, own downloads, complete audit linkage and once-only recovery after later progress. Additional cases cover expired signer sessions, corruption/evidence failures, lease loss/forgery, rollback/lost commits, queue/hint outages, suppression, stale current pointers, isolated read scopes and database ownership/retention ordering. A synthetic invitation is also delivered through local Mailpit only.

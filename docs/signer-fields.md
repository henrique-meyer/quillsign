# Deliberate signer field application and review

QUILS-32 adds `SignerFields.GetAsync` and `ChangeAsync`; QUILS-33 connects them to `/sign/{publicId}/fields` and `/sign/{publicId}/review`. Adoption and field application remain separate actions: each call applies or clears exactly one field owned by the current signer. GET/snapshot reads never fill fields. Finish, PDF mutation and completion mail remain subsequent work.

Every operation requires current sequential eligibility, recorded consent, a live bound signer session and the unchanged frozen PDF/disclosure. It uses the common envelope lock. Snapshots contain only that signer's fields, including normalized placement, labels/required flags, current rowversions, saved values and stale mark bindings. Invalid page metadata/bounds and more than 200 fields fail closed. Sender-prefilled and other signers' fields are excluded.

`SignatureAdoption.ReadCurrentAsync` provides authorized access to the current adopted mark pair after its original ten-minute preview expires, including from a fresh authorized session. It verifies the current signer pointers against the used preview, frozen PDF/disclosure, supported versions, matching signer-attributed adoption event/content hash/statement and exact stored PNG hashes. The event is matched by adoption ID, not timestamp equality: adoption time and audit-event time can differ with a real clock. This read does not refresh a preview or authorize a new adoption. Replaced/unadopted or malformed evidence cannot be returned as current.

Asset reads use the existing short-lived, exact-object internal capabilities. Ordinary signer cookies still cannot write/delete/read signature objects directly. Current-mark reads stage bounded image bytes before returning them and recheck scope after storage. Missing, altered or oversized assets cannot be applied. The existing adoption page also handles `InvalidDataException` from hash/length verification as a recoverable storage error; no false adoption success is reported.

A change names one field ID, its base64 rowversion and an explicit Apply/Clear action. Signature/initials Apply also requires the **current adoption ID** and accepts no client value/blob reference. The server resolves the correct object and hash from verified adopted assets. It saves the value internally as the object ID plus separate adoption-ID/SHA-256 columns, server `FilledAt` and signer `FilledBy`, then appends `field_filled` atomically. Public snapshot mark values omit internal object references.

Replacement preserves existing field records/evidence but makes their older mark bindings stale. A stale mark is not reported as filled. Each requires another explicit application with the new current adoption ID and field revision. Adoption/replacement never bulk-fills, clears or automatically updates signature fields. Clear is a separate audited action that removes value, fill metadata and mark binding; it can clear an old stale field without asserting a replacement mark.

Text values are bounded to 4,000 UTF-16 characters, strict Unicode, NFC and LF line endings, preserving meaningful whitespace and allowing newline/tab while rejecting other control/format characters. An empty/whitespace text value does not count as filled. Checkboxes accept exactly `true`/`false`; both are explicit values, distinct from clearing. Generic calendar fields accept valid invariant `YYYY-MM-DD` values. Full Name is derived from the sender-provided signer record and rejects any client override. Date Signed is read-only and remains pending until the server's eventual Finish time; client timestamps are never accepted.

Matching current canonical state returns AlreadyApplied without another audit event, including concurrent exact retries. A stale revision with a different value returns Conflict; a replaced/forged adoption returns InvalidAdoption. Storage/audit failures roll back field changes, and a lost SQL commit acknowledgment can be retried without recording another event. Audit evidence includes field/type, prior/new canonical value, mark binding/image hash where applicable, value hash and frozen PDF/disclosure hashes, attributed to the signer. Values belong in private application records, not request logs or repository fixtures with personal data.

The migration adds paired mark-binding/hash columns, a binding check and a composite foreign key tying each applied mark to a preview from the same signer/envelope. Retention must delete fields before previews and signers; existing applied previews/assets/evidence are preserved until that purge. No recurring SQL maintenance or new cloud resources were added. Existing runtime field permissions cover the new columns; preview contents retain their restricted permissions.

SQL Server/Azurite tests cover ownership/session/consent/sequential scope, current assets after preview expiry, nonidentical server/audit times, concurrency/idempotence, stale replacement/reapplication/clear, server-derived/manual values, invalid payloads/pages, database binding constraints, missing/tampered/oversized assets/evidence, audit rollback and uncertain commits. Signer status/`SignedAt`, frozen PDF and unrelated fields remain unchanged.

## Enter and review fields

The field page verifies the saved PDF and current adopted mark pair before showing them. PDF.js displays the unchanged frozen document, with saved-entry overlays positioned in normalized visible-page coordinates. Zoom/page navigation and selecting overlays or the accessible field list only select a field. **Apply signature/initials to this field**, **Apply my full name**, **Save this field** and **Clear saved field** are separate deliberate actions. Next incomplete field skips Date Signed, which stays pending for server Finish time. Missing/stale counts and field statuses describe saved state, never unsaved browser edits. Both an explicitly checked and an explicitly unchecked checkbox count as a saved response.

The client serializes changes, disables controls while saving and sends antiforgery tokens, field revisions and current adoption IDs. Labels and values use text nodes/encoded Razor output. Validation errors preserve attempted entries. Conflicts return the latest owned saved value without overwriting; storage/network uncertainty blocks another save until **Refresh saved state**. Refresh preserves unsaved text/date/checkbox attempts and requires another explicit action to apply them. There is no automatic conflict retry, replacement application or optimistic success. An inline navigation choice protects unsaved entries when leaving for capture, review or disclosure; the browser also warns on unload while unsaved edits or a save are pending.

Review reloads server state, verifies the bound PDF/current marks, and shows only the current signer's entries, required/missing/stale status and corrective field links. A replaced mark is labeled stale and its prior pixels are not presented as a current saved mark. Date Signed is visibly reserved for Finish. The overlay is not a stamped or sealed PDF. The [exact review and Finish flow](signer-review-finish.md) separately prepares the immutable PDF and requires deliberate review/intent before accepting Finish.

Field/review operations use isolated signer authorization, no-store/no-referrer and a separate bounded per-IP interaction window of 120 requests per minute, allowing multi-field flows without consuming the signature-capture request window. HTML success redirects to a clean URL with a once-only HttpOnly notice; JSON clients receive the result in the body. Receipts/action notices are not added to URLs. Current asset reads still use narrow internal capabilities rather than signer-cookie blob access.

TestServer cases cover private read-only pages, CSRF, exact current PNGs beyond preview expiry, single-field apply/clear/idempotence, clean notices, conflicting revisions, replacement/stale review, canonical text/checkbox/date/server-derived name values, read-only Date Signed, context/ownership isolation and recoverable storage/throttling errors.

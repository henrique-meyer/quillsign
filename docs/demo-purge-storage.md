# Bounded demo purge storage

This is a storage dependency, not automatic document deletion. There is no public endpoint, registered purge handler or maintenance schedule. It does not remove SQL transaction/contact/evidence data or enable hosted maintenance. [Retention enrollment](document-retention.md) still supplies the immutable first-upload decision.

[Authenticated recovery markers](demo-purge-recovery.md) now support explicit storage-only retries through the bounded adapter. Actual scheduling and private SQL deletion remain a following coordinator slice.

`DemoPurgeAuthority.AuthorizeLockedAsync` requires a caller-owned SQL transaction, a genuine currently owned `Purge` work lease and its exact canonical envelope/policy payload. It locks the parent before the work row, verifies the saved upload policy and audit provenance, rejects ordinary and unenrolled records, and requires the saved UTC deadline to have arrived. Environment changes cannot extend or replace that decision. The resulting sealed storage scope expires at the earlier of two minutes and the work lease; it is separate from all sender, signer and final-file read/write identities.

`AzureEnvelopePurgeStore.SweepAsync` accepts that scope and a maximum of 1–128 inventory entries. It visits only the exact opaque envelope prefix in `originals`, `normalized`, `previews` and `final`. This includes obsolete/replaced assets and completion subpaths independently of current SQL file references. Continuations remain bound to the envelope/policy and area; inventory names and exact ETags are checked before constructing object clients. It never lists the whole container, reads document bodies, creates resources or deletes containers.

The adapter inventories snapshots and versions, reads exact object properties and uses conditional deletes. Legal holds and future immutable deadlines remain protected; changed objects remain incomplete, and other service failures propagate without a successful result. It does not clear policies, remove holds or invoke permanent-delete bypasses. Missing owned objects are idempotent. Cancellation and scope expiry are checked around I/O; an effective deletion followed by a lost response or expiry can be recovered by a fresh authorized pass.

Azure keeps previous versions when the base blob is deleted, so those versions must be enumerated separately. Soft-deleted versions remain subject to the provider's retention interval. These semantics are described in [Microsoft's versioning documentation](https://learn.microsoft.com/en-us/azure/storage/blobs/versioning-overview) and [delete operation documentation](https://learn.microsoft.com/en-us/rest/api/storageservices/delete-blob). The adapter does not claim immediate erasure of backups, soft-deleted data, provider-expiring uncommitted blocks or logs, and changes no hosted permissions or protection settings.

`ReachedEnd` describes one observed inventory pass. It is **not** proof of permanent envelope purge: an old producer can still finish a write after that scan. Snapshot/base ordering, current/previous versions, changed ETags and partial failures can also require another pass. The following coordinator must persist minimal non-personal recovery state, re-scan late-owned writes, preserve retries beyond ordinary finite work attempts and safely remove associated private SQL data. A single empty pass or arbitrary grace sleep cannot replace that recovery contract. Reads never schedule cleanup, and future maintenance must preserve SQL idle auto-pause.

Validation uses synthetic enrolled records with real local SQL/Azurite for authority, bounded inventory, snapshots, deletion, late-write re-scanning and unrelated-record preservation. Controlled HTTP transport exercises the actual Azure SDK's version/snapshot targeting, conditional requests, protection and failure responses. That is not live Azure immutability/RBAC validation; hosted rollout remains separately approved work.

# Isolated preservation provider validation

QUILS-155 tests provider prerequisites for the unfinished QUILS-147 legal-hold lifecycle. It does not activate production holds or establish release readiness. Approval must identify the existing account/user, new container, temporary permissions, irreversible protection consequences, time/request/version/byte limits, cost allowance and delayed cleanup before any deployment or provider call.

The standalone `infra/hold-provider-pilot.bicep` template creates only a new private version-immutability-capable container and an existing user's temporary Storage Blob Data Owner assignment scoped to it. It is not included in normal hosting deployment. Store actual parameter values and receipts outside Git. Reject an existing container rather than updating it. Native what-if must contain only those two additions. The account, hosted application, existing containers, SQL, identities and protection/recovery policies remain unchanged.

The temporary role allows more than blob reads/writes, including version-policy management. Existing inherited permissions remain a separate consideration; a new container is not isolated from principals with broader account access. The pilot uses synthetic data only, Entra authentication and no credentials or SAS tokens in files or logs. Remove the exact temporary assignment after the test, including failure.

A guarded local runner owns a durable manifest and consumes counters before possible provider operations, including retries and uncertain writes. It must bind the approved container/test prefix and exact returned version IDs. Never run the current production archive writer against hosted final records to perform this experiment. Exact byte hashes, lengths, version IDs, ETags and actual protection must be read back; an SDK success or mocked provider is insufficient.

Create immutable synthetic witnesses separately from disposable archive versions with legal holds. Locked witness expiry must be recorded before each write and cannot be shortened for cleanup. Legal-hold changes may leave ETag unchanged, so protection needs independent readback. Root overwrites may create new versions; verify the retained original and reject conflicting history rather than trusting the latest root. Do not change an existing record's policy or protection.

Restoration validation compares the complete external test namespace with authenticated journals in disposable local SQL, including an earlier snapshot and a wholly missing record. Missing or conflicting witnesses, rollback, unmatched prepared intents, provider uncertainty and independently blocking holds must deny destructive authority. Passing this experiment does not implement the remaining application mutation/deletion fences, operator middleware or effective/released lifecycle.

One separately approved cleanup pass runs after the latest recorded lock expiry and safety interval, within the original aggregate limits. It may remove only listed expired synthetic versions and their separately recorded disposable legal holds. Unexpected contents, state or identity stop cleanup. Keep soft-delete settings unchanged, preserve receipts and do not equate API deletion with physical erasure.

# Restricted signing pilot

This optional operator workflow tests synthetic signing with public `Email.Enabled=false`. It does not make the demo available for real agreements or enable public intake. AI placement remains deferred. All settings default off; the example configuration contains empty private fields.

`EmailPilot` selects one private run ID, four distinct normalized test mailbox roles and the SHA-256 of a random 32-byte base64url operator capability. Keep the capability, hash, run ID and real addresses outside tracked files. Configure the existing persistent key ring, SQL, work signals, SES sender/configuration set, electronic-record policy, final storage and timestamp service before use. Recipient verification and provider account restrictions still apply.

Open `/operator/pilot` over HTTPS. Enter the capability in its password form. Unlocking creates only a fixed, purpose-protected HttpOnly operator cookie; anonymous GET and unlock do not create a run or send mail. The operator cookie grants no sender, signer or document-reader authority. The status page is private, rate limited and excluded from public previews and analytics. Forms require CSRF protection. Capabilities are form-body input only and must never be put in a URL, log or screenshot.

The first explicit scenario/simulator action creates the immutable sixty-minute run and durably prepares its delayed seven-day encrypted-secret cleanup before admitting mail work. Retry the same action after an unconfirmed result: deterministic identities recover existing work and never reset the deadline or counters. GET only reads status. Cleanup uses existing event-driven scheduling and a worker-only guarded procedure, not idle SQL polling. Nonpersonal immutable run/enrollment/accounting evidence remains after the encrypted manifest is removed; ordinary document retention remains separate.

The three fixed scenarios are two-signature completion, sender void and signer decline. Each begins with an ordinary sender verification message. Complete the normal mailbox confirmation, manual document preparation and field placement, affirmative disclosures, signature adoption, deliberate field application, exact review and Finish. The completion scenario permits exactly two ordered test signers plus the completion-only recipient; void and decline permit only the first test signer. After actual publication, one explicit lookup action can send the sender a normal lookup link restricted to that completed packet. No caller supplies an address or arbitrary envelope to an operator action.

The three simulator actions use fixed SES delivery, bounce and complaint simulator destinations and attach no documents. Signed feedback ingress, provider receipts and suppression evidence must be checked separately: feedback that races receipt persistence is not guaranteed to update an outbox row unless it is redelivered. A saved work request is not a delivery confirmation.

Limits are fixed in code: twenty application recipient submissions, ten simulator submissions, four timestamp attempts, one MiB per complete encoded MIME message, thirty MiB aggregate mail and at most three synthetic envelopes. These limits bound selected provider operations; they are not a dollar billing cap. All actual mail uses the same immutable MIME artifact measured by the ledger. Each owned work attempt reserves before lazy credentials/provider access. SDK sending retries and redirects are disabled. Unknown provider outcomes and lost commit acknowledgements retain consumed attempts and cannot grant a repeat submission. Timestamp calls are bound to the actual owned completion work and artifact.

Every enrolled sender, signer, lookup and completed-record read remains bounded by the original run, including expiry/disable during asynchronous preparation. Existing links never become ordinary authority when pilot settings are disabled or rotated. Keep the runtime safeguards installed after stopping a pilot; disable `EmailPilot.Enabled` and the provider configuration set, and preserve public `Email.Enabled=false`. Closing the operator cookie alone does not stop already admitted work.

Deployment requires the pilot ledger/lookup migrations, existing guarded cleanup procedure, read/insert runtime grants and worker-only cleanup execution. Apply only the reviewed deployment package to the existing approved resources. Source tests and local captured-provider/browser evidence do not prove hosted mail delivery, signed feedback, live timestamps or production publication. Record those separately during the bounded hosted run, then restore disabled sending and report the actual results and remaining limitations.

## Lower allowances for an approved continuation

`EmailPilot:Allowance` can lower `ApplicationAttempts`, `SimulatorAttempts`, `TimestampAttempts` and `EncodedBytes` from their original hard maxima. Environment names use `EmailPilot__Allowance__` followed by the property name. Zero closes that category; negative values or values above the existing maxima are invalid. The one-MiB individual message limit does not change. Defaults still permit twenty application submissions, ten simulator submissions, four timestamp attempts and thirty MiB of complete MIME.

An operator must reconcile all prior nonrefunded consumption and stay within the owner's existing run/window authorization; this setting does not create or renew one. Configure the same reviewed remaining allowance on web and worker before admission. The protected manifest snapshots that allowance, and subsequent configuration changes fail closed instead of changing a saved run. Transactional reservations enforce it before mail credential access or timestamp HTTP, including background retries. The private status counters report the protected allowance without exposing the manifest.

Legacy manifests retain their original canonical bytes/hash and original hard allowance. They are not rewritten into a lower profile; using mismatched allowance settings does not reopen them or refund earlier work. No migration or new database grant is needed for the optional protected-manifest extension.

# Signature preview and adoption backend

QUILS-30 adds `SignatureAdoption.PrepareAsync`, `ReadAsync` and `AdoptAsync` as internal workflow services. There is no public adoption endpoint, browser capture UI, field application, PDF mutation or Finish action in this slice. A future UI must display the returned server-normalized signature and initials plus the exact statement before collecting an explicit adoption action. Preparing or fetching a preview records no adoption.

Every operation requires a current sequential signer, a live isolated signer session, the unchanged frozen PDF/disclosure and recorded consent. Each newly redeemed invitation gets a random session nonce preserved in its protected cookie; another session with the same signer, document and expiry cannot reuse a preview receipt. Older cookies without this nonce are rejected and require a fresh invitation. Receipts and signature pixels must not be logged.

Preparation normalizes both PNGs through [the bounded PNG processor](signature-assets.md), then stores fresh immutable objects in the existing private `normalized` container. It reads back and checks both hashes before saving the preview and returning the exact bytes. Typed descriptors are trimmed/NFC-normalized, with limits of 200 characters for the name and 20 for initials; other methods cannot carry typed descriptors. These values describe the reported input method and do not overwrite the sender-supplied signer name or establish identity.

A preview binds the signer/envelope, session fingerprint, frozen document/disclosure hashes, signer rowversion, image dimensions/hashes, normalization version and adoption-statement version. Its ten-minute lifetime is clamped to the original session expiry. Reads do not extend it. Envelope locking bounds creation to five live unused previews and forty total previews per signer per envelope, including expired history. Reaching the total cap requires reuse of a still-current unexpired preview or contacting the sender; waiting alone does not reset it. The later UI should prepare only after an explicit preview request, rather than on every keystroke.

Ordinary signer cookies still allow only frozen-PDF reads. The workflow creates an in-process storage capability for exactly one signature/initials object and one read, write or delete operation. Capabilities last at most two minutes, are never authentication cookies/serialized claims, and deny other objects, kinds, envelopes, operations, copied or mixed identities and expired access. Read/write capability expiry is also clamped to the session; rollback cleanup gets a fresh internal delete capability only for each newly attempted object. This uses existing storage resources. Known rollback removes these objects where possible; uncertain SQL commits retain potentially referenced assets. Unreachable objects remain for future envelope purge. No background SQL polling was added.

Adoption requires the protected preview receipt and an explicit acknowledgment of statement version `2026-10-16.1`:

> By selecting Adopt and Sign, I agree this mark is my electronic signature and initials, legally equivalent to my handwritten signature.

Under the common envelope lock, adoption verifies current scope, consent, expiry, signer revision, preview versions and both exact stored image hashes again. One transaction saves the current adoption ID, asset references/hashes, method, reported typed descriptors, versions and server time, marks the preview used and appends signer-attributed `signature_adopted` evidence. Evidence contains the exact statement/text hash, image hashes/object IDs and frozen PDF/disclosure hashes. It records a request received from the consented email-link session, without claiming that the server observed a human reading the screen. Concurrent calls and retries of the current unexpired adoption record once, including retry after a lost commit acknowledgment.

Replacing a mark requires a fresh preview of the current signer revision. Replacement records the previous adoption ID, preserves older assets/previews/audit evidence until purge, and invalidates stale or parallel previews. Future deliberate field application must bind each click to the current adoption ID and image hashes and reject stale references after replacement. Adoption leaves signer status, `SignedAt`, fields and the frozen PDF unchanged.

Apply the migration before use and rerun the existing `database grant-runtime` provisioning step with the authorized administrator connection. Runtime grants allow preview SELECT/INSERT/DELETE and only the `UsedAt` column to be updated; preview contents cannot be updated through runtime permissions. Cloud deployment/provisioning was not performed by this change.

SQL Server/Azurite tests cover normalization/receipt/session binding, context changes, count/lifetime limits, capability isolation, storage verification/loss/tampering/size bounds, rollback cleanup, uncertain commit recovery, concurrent/idempotent adoption, replacement, immutable preview contents and audit rollback/retry. UI validation remains part of the later UI story.

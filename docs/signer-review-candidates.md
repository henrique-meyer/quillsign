# Immutable signer review candidates

QUILS-35 adds an internal preparation/read service for the later review and Finish workflow. It exposes no HTTP endpoint or UI and makes no field, signing-status, invitation, email or seal changes. A preparation audit event records server preparation; it does not assert that a person reviewed or signed the PDF.

Explicit preparation takes the common envelope transaction lock and verifies the isolated signer session, request, nonce, consent and sequential eligibility. All required owned fields must already be deliberately saved, except server-controlled Date Signed. At least one current Signature field must be applied. Current signature/initials assets must pass the existing adoption evidence and exact normalized PNG/hash checks. The source PDF is independently read and hash-verified. Only locked server records supply field values, revisions, geometry and Full Name.

The renderer stages a fresh immutable PDF, independently reads back its complete bounded bytes, and stores its object ID, length, SHA-256, source/disclosure/session/snapshot/recipe hashes, adoption ID, renderer/snapshot versions, preparation time and expiry. The candidate and signer-attributed `signer_review_prepared` audit evidence commit together. The source PDF and saved fields remain unchanged. A data-protected receipt binds that exact candidate to the current signer/session nonce; it belongs in a private request body, never a URL or log.

Date Signed in this review copy is **prospective**, using the preparation server's UTC calendar date. The receipt expires at the earliest of ten minutes, session expiry, envelope expiry or the next UTC midnight. A later explicit Finish must compare its actual server UTC date with the reviewed date and atomically consume the candidate. Preparation does not record a signing instant or fill Date Signed. A midnight rollover requires a newly prepared review copy.

Preparing the same unchanged live snapshot in the same session reuses the exact stored candidate and audit event. Each owned field's full saved state and revision, signer name/consent/revision, source/disclosure and current adoption contribute to the snapshot hash. Changed saved state invalidates old reads; new preparation supersedes active older snapshots. Replacing adopted marks requires deliberate reapplication of every affected field. Different session nonces cannot share a receipt. At most two live candidates and twenty total candidates are allowed per signer; exact live reuse remains available at the limit. Reads do not refresh expiry or mutate records.

Candidate retrieval rechecks current consent, scope, eligibility, snapshot, adoption and preparation evidence, then verifies the exact complete PDF length/hash before returning bytes and rechecks live context after storage. Missing or changed objects, assets, evidence, expired/consumed/superseded receipts and changed revisions fail closed. Ordinary signer cookies retain their existing source-PDF-only storage authority. Short-lived in-process capabilities authorize only one exact review PDF object and operation; copying claims does not copy that authority.

Known preparation rollback attempts delete only the newly staged candidate object, including after session expiry. If commit acknowledgment is lost, possibly referenced bytes remain intact and an unchanged retry recovers the committed candidate. Failed cleanup leaves unreachable bytes for the envelope's eventual privileged purge. No background polling or cleanup worker is introduced here.

The migration enforces envelope/signer/adoption ownership, hash lengths, PDF limits, object uniqueness, expiry/UTC-date bounds and consumption/supersession state. EF rejects changes to saved candidate content; runtime SQL permissions allow updates only to consumption/supersession timestamps. A privileged retention path must delete review candidates and fields **before** signature previews, then signers and the envelope, and purge all envelope objects, including expired candidates or failed-cleanup objects. This slice documents and tests that ordering without introducing a retention policy or worker.

SQL Server/Azurite tests exercise required entries, concurrent idempotence, nonce/scope isolation, revision/replacement invalidation, exact rendered bytes, UTC rollover and expiry, active/lifetime limits, storage/audit rollback, lost commit recovery, immutable ownership constraints, preparation evidence and narrow storage authority. Actual operator disclosure policies remain empty; this service does not make an operator configuration valid for public sending.

# Capture and adopt signature marks

After electronic-record consent, **Adopt your signature** opens `/sign/{publicId}/signature`. It offers Type, Draw and Image tabs for a signature/initials pair. Arrow keys, Home and End select tabs; Tab enters the selected panel. Type is the keyboard-accessible capture option and shows unsaved appearance samples; Draw accepts a mouse, pen or touch and provides separate Clear controls. Drawing data is rescaled when the viewport changes instead of silently clearing strokes. Canvas dimensions/device-pixel ratio stay bounded. Phone/SMS handoff is deferred.

Type renders the entered name/initials in the browser's cursive font into an sRGB canvas. Font fallback may vary between browsers; the exact saved server preview is authoritative. Names/initials use bounded NFC plain text. A mark too long to display clearly is rejected with a recoverable message. Typing, drawing, uploading, changing method and opening the page never adopt a mark.

Upload accepts static PNG/JPEG files up to 5 MiB and 2048 × 1024 pixels each. The browser checks bounded format headers/dimensions before decoding, rejects PNG animation controls and unsupported/incomplete headers, checks decoded dimensions again, and converts the decoded image to sRGB RGBA PNG. PNG transparency and aspect ratio are preserved. Converted PNGs must each fit the 512 KiB server contract. Original uploads/metadata are not stored; the saved pixels may still contain information present in the mark. The server independently applies the strict [PNG normalization rules](signature-assets.md).

**Prepare saved preview** submits both PNGs with antiforgery protection. The [adoption backend](signature-adoption.md) saves and verifies the assets, and the page reads the protected preview back before returning exact saved PNG bytes. Only after both returned images decode does the page reveal their preview and the versioned adoption statement. An initially unchecked acknowledgment enables **Adopt and Sign**. Input edits clear the displayed preview/receipt/acknowledgment; expiration disables adoption and requires an explicit new preview. No autosave or automatic adoption runs.

The saved-preview form prefills the trusted sender-provided signer name in a read-only field. The signer explicitly confirms that name and separately acknowledges the adoption statement. If the name is wrong, they must contact the sender; capture never changes the frozen signer identity. The server requires both confirmation and an exact match to the current trusted name. Input/method edits, expiry and restored browser history clear both acknowledgments. This confirmation is a product safeguard, not a claim that drawing or uploading legally requires typing the name again.

Adoption posts the protected receipt, name confirmation, acknowledgment and statement version through the isolated signer scheme. Successful HTML requests redirect to the clean signature URL with a short-lived HttpOnly notice shown once; JSON clients receive a body. Missing, expired, foreign or stale evidence cannot adopt. Storage failures display a recoverable error, including an instruction to reload and check state after an uncertain commit. Repeated clicks are blocked while requests run, with backend idempotence as the final protection. Returning through browser history clears stale client confirmation state.

Every operation rechecks current consent, session, sequential eligibility and frozen PDF/disclosure scope. GET creates no previews or adoption. Requests/responses use no-store/no-referrer; receipts and pixels stay out of URLs/logging. Signature POSTs share the configured per-IP sender rate policy and return recoverable HTML/JSON throttling responses. Existing preview count/lifetime caps also apply. Ordinary signer cookies retain frozen-PDF read-only storage access.

After adoption, the page reports that the marks are adopted and signing is incomplete, and links to [deliberate field application and saved-entry review](signer-fields.md). A replacement requires a new preview/acknowledgment and preserves earlier evidence. It makes earlier field applications stale until each is explicitly reapplied or cleared. The capture UI never marks Signed, fills fields, mutates a PDF or sends completion mail. Adoption remains separate from explicit Finish and sender Send.

Drawing uses [signature_pad 5.1.4](https://github.com/szimek/signature_pad), MIT licensed. Build restores the pinned npm archive without package scripts into ignored `obj/browser-assets`, checks archive/file hashes, and distributes the original module and complete MIT notice. Integrity metadata is in `Build/signature-pad.manifest.json`; verify a build with `python scripts/dev/verify_signature_pad.py src/QuillSign/bin/Release/net10.0/wwwroot/vendor/signature-pad`. No browser runtime CDN request is used.

Validation covers real typed/PNG/JPEG/drawn browser preparation and adoption, keyboard-only adoption, desktop/mobile layouts, edit invalidation, missing initials, oversized upload rejection, drawing clear/retry and resize preservation, and missing-storage recovery on synthetic nonbinding requests. SQL Server/Azurite/TestServer cases verify CSRF, sender/signer/consent isolation, exact returned PNGs, expiry/session/statement binding, replacement, truthful state/notices, JSON behavior and rate limiting. Node tests check predecode image bounds and malformed/animated source headers.

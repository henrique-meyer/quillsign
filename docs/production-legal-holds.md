# Production legal holds

This is the QUILS-147 design and internal component checkpoint: private pending commands, SQL/object inventories and isolated SQL, manifest and raw-object archive provider adapters. It does not activate a hold service, install operator routes, provision an identity provider, change live cloud protection, or establish production readiness. Coordinated complete-bundle preservation, historical-reference coverage, durable bundle/control receipts, external fencing and effective/released lifecycle remain required before the QUILS-148 operator workflow.

## Operator authentication

Self-hosting operators will use a separate OpenID Connect authentication scheme with a dedicated protected operator cookie. The operator feature defaults to disabled. The callback must validate the configured authority, signature, audience, nonce, state and exact issuer through the standard authentication middleware before an operator ticket can be issued. No participant token, pilot capability, generic application identity, forwarded identity header or public administrator signup grants operator authority.

Operators configure exact issuer/subject pairs and explicit permissions. Status, hold placement, hold release and sensitive evidence reading are different permissions. A hold administrator does not automatically gain document-content access. The application supplies no operator identity, authentication tenant, legal policy, retention interval or reason text. Identity-provider authentication/MFA policy belongs to the operator; activation requires a reviewed deployment.

The internal authority adapter accepts only a ticket from that dedicated protected-cookie scheme, an authenticated identity from the dedicated OpenID Connect scheme, an exact configured issuer/subject match, a current ticket issued within the five-minute operator session bound, and an explicitly allowed permission. It caps the resulting authority at the earlier of ticket expiry and five minutes. This adapter is not itself an OIDC token validator: the future operator middleware must establish and protect the ticket. Until that middleware exists, the adapter is internal and unregistered.

Privileged POSTs will require same-origin antiforgery, rate limits and explicit confirmation. GET never places or releases a hold. Exact record, hold, operation, command ID, expected hold-state revision and a digest of the private reason/reference must be bound into an expiring one-use confirmation. Release requires its own permission and confirmation. Replaying a different command under the same ID is a conflict, not success. A stored command receipt must still be authenticated before an idempotent recovery is reported.

## Preservation and concurrency requirements

Hold placement must immediately fence new deletion decisions under the same parent-record lock, then verify and protect the entire evidence bundle: original and normalized documents, current copies and checkpoints, final versions, adopted/replaced referenced marks, disclosures, acceptance/publication/audit evidence, and required participant/contact history. A database placement request is only preservation-pending until the exact inventory and provider protections are verified. It must not be reported effective for evidence already deleted or of uncertain completeness.

The durable backend must maintain append-only command/protection evidence, attributable private actor/purpose/reference details, an exact authenticated record revision, and a monotonically changing deletion fence. An uncertain commit is reconciled against the saved command and evidence rather than blindly reissued. Unknown protection, partial deletion or mismatched state blocks deletion and stays visible to operators. Case reasons and private operator subjects must not enter participant pages, final PDFs, public logs or unauthenticated status.

The current internal request ledger persists authenticated-encrypted operator/command details separately from the participant audit. Every request binds the saved production policy, exact parent/hold/command IDs, original expected global revision, timestamp and previous-entry digest. Reads require verified enrollment and the common parent lock; exact replay returns the saved request rather than advancing its clock or revision. Missing, demo and unenrolled records cannot acquire an implicit policy. Ordinary runtime and worker SQL roles have no access to this private table. A separately approved privileged executor is still required before any runtime registration.

This ledger reports only preservation-pending and release-pending requests. Both remain deletion-blocking. It provides no effective-preservation or completed-release receipt. Its bounded authenticated journal rejects corrupted entries and missing prefixes; it cannot independently detect wholesale restoration of an earlier valid database. External storage fencing and restore reconciliation in the remaining backend/acceptance work must address that case before deletion is enabled. Source migrations create the table; they do not grant operator access or change a hosted database.

The private SQL inventory builder verifies that exact pending fence and captures all explicitly covered record-owned scalar rows under the parent transaction and SQL range locks. It checks row/byte bounds before loading, includes column/type descriptions and per-table content digests, and returns authenticated encrypted output. The content fingerprint excludes capture time so a later source change can be distinguished from a repeated capture. It includes the record's own linked lookup-retention metadata, never global suppression or unrelated lookup/pilot data. An unexpected model or pilot association fails closed. It neither repairs provenance nor changes a retention clock, session, source row or audit event.

An encrypted SQL snapshot alone is not complete preservation. The remaining worker must verify every required referenced object/version, maintain external fencing against restore and concurrent mutation/deletion, bind the exact SQL and object inventories to durable protection receipts, and reconcile uncertainty before reporting an effective hold. Unknown provider protection or missing objects must keep the request pending or failed and deletion blocked.

Every active hold blocks deletion independently. Explicit release resolves only its exact hold; other holds continue to block. It cannot shorten time-locked protection, change original retention clocks, rewrite signed evidence, restore participant sessions or grant public access. Ordinary indefinite retention is independent of a case hold. Releasing the final hold triggers reevaluation of the frozen policy, not an immediate destructive operation.

QUILS-149 must honor the same fence before each exact destructive action and storage-recovery boundary. Runtime database roles cannot edit or delete hold evidence directly. A complete implementation must cover placement/deletion races, independent holds, stale/replayed confirmations, permission revocation/expiry, restart and uncertain commits, provider failure, missing evidence, and release during unexpired retention. Source/local synthetic acceptance is distinct from hosted provider permissions and physical backup erasure.

## Read-only object evidence component

Next internal object-evidence step: build an unregistered read-only Azure adapter that inventories only the exact record prefix across originals, normalized, previews and final, including versions/snapshots, with bounded pages/object counts/bytes, private-container checks and conditional exact-version streaming SHA-256. Bind its result to an authenticated SQL snapshot and verify compiled named original/normalized/sent, adoption/review/Finish, seal-stage and final-publication references. Re-list to reject observed late changes; never treat repeated listing as an atomic storage fence or immutable preservation. Reject missing/changed/partial evidence and unsupported selectors. This remains a pending component: complete historical opaque-payload reference coverage, durable provider archive/protection receipts, external restore fencing, continuing-mutation coordination and effective/released states are still required before activation or merging the story.

The object component uses the SDK HTTP-header ETag format consistently because list XML and download responses can quote the same tag differently. It includes deleted/version-only roots and rejects unreadable tombstones, public/missing/denied containers, unsupported object types and partial inventories. The saved object result retains its exact encrypted SQL snapshot so a future archive can preserve the same payload rather than recomputing a different capture-time hash. A second census and SQL fingerprint check detect observed changes; actual storage fencing and immutable provider preservation are still absent.

Azure API references: [version and snapshot listing](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-blobs-list?tabs=dotnet), [ETag formatting](https://learn.microsoft.com/en-us/dotnet/api/azure.etag.tostring?view=azure-dotnet), and [SDK ETag representation report](https://github.com/Azure/azure-sdk-for-net/issues/29942). These document read semantics; they are not evidence of configured provider protection.

## Isolated SQL archive component

Next provider step: implement an unregistered create-only private SQL-archive adapter. A worker capability must authenticate the exact encrypted SQL snapshot against the current pending hold/command/revision/fence under the parent transaction. Store only its exact ciphertext/hash in an isolated production-holds/ prefix outside the record source prefix, in the existing private version-immutable final container. Stage bounded bytes, commit only after EOF/hash validation with If-None-Match and a legal hold on the newly created version, then verify exact provider version/ETag/legal-hold facts and actual bytes. Lost acknowledgements recover by exact readback; insufficient/missing/changed protection remains failed. Never set/clear protection on existing business objects, shorten time retention or provision containers/grants. This protects only the SQL archive component: raw-object archives, durable complete-bundle/control receipts, external restore fencing and actual effective/released lifecycle remain required before activation/merge.

Provider API references: [create-time legal hold on Put Block List](https://learn.microsoft.com/en-us/rest/api/storageservices/put-block-list) and [version-level immutable-storage prerequisites](https://learn.microsoft.com/en-us/azure/storage/blobs/immutable-policy-configure-version-scope). Hosted support and permissions require separate rollout verification.


SQL archive provider component implemented: all 128 focused cases pass warning-free (111 inventory/journal/authority/schema cases plus 17 archive cases). Its internal worker capability authenticates the frozen ciphertext and current SQL/hold fence, rejects pending release and stale/tampered evidence, and can reauthorize the SAME historical ciphertext after fresh current-state verification without renewing participant access or retention. The Azure adapter creates only isolated private version-level legally held SQL archive blobs, verifies exact version/ETag/bytes/protection, rereads protection after content because legal-hold changes need not alter ETag, and reconciles lost acknowledgements/concurrent exact creation. Expiry during staging/commit stops further IO and requires fresh authorization. Tests use actual disposable SQL and intercepted SDK transport, not live Azure immutability. Complete raw-object preservation, durable authenticated bundle/control receipts, external restore fencing, mutation/deletion coordination and effective/released lifecycle remain incomplete; no runtime activation or hosted change.

## Raw-object and manifest archive component

Next raw-object/manifest preservation step: authenticate and validate the entire encrypted object-manifest envelope, its exact SQL snapshot, summary and owned selectors before issuing a fresh private worker capability under the current pending-hold fence. Preserve the original encrypted manifest plus every selected raw source version as isolated create-only legally held archive versions outside recordGuidN/. Share the verified provider-write implementation with SQL archives; source reads must use the exact manifest area/path/version-or-snapshot/ETag/length and the expected SHA-256 before any archive commit. An already verified retained archive may recover without rereading a subsequently missing source; no fallback to other source versions. Reject tampered manifests, unlisted selectors, stale SQL/release-pending state and missing/changed/truncated/extra source bytes. Provider facts remain incomplete until separately authenticated durable bundle/control receipts, full historical-reference coverage, external restore and mutation/deletion fencing and actual effective/released lifecycle are implemented. Source/local tests only; no runtime activation, cloud changes or new container/grant.

Provider tests use intercepted SDK transport; no live Azure legal hold was changed. This still supplies component facts, not a durable complete-bundle or effective-hold receipt.

## Durable bundle control journal design

The next internal component is a private append-only control journal, separate from the request journal and participant audit. A frozen plan persists the bounded exact encrypted SQL capture and object manifest, current placement command/fence and deterministic archive item descriptors before archive copying begins. Restart resumes the same plan and payloads. Item receipts bind only exact provider-verified archive versions, ETags, lengths, hashes and legal-hold facts to their plan; a guessed path or returned SDK success is insufficient. Conflicting replay fails rather than replacing a plan or receipt. Unknown commits reconcile the exact saved event under the common parent lock.

Version the SQL inventory envelope to carry a separately authenticated control prefix/head. Keep every existing business and request row in the business fingerprint; exclude only explicitly covered control publication from that fingerprint to avoid a snapshot/receipt self-reference. Current authorization must authenticate the whole control chain and prove extension of the captured prefix. Prefix omission, alteration or rollback is a failure. Bound row counts and ciphertext/decoded payload bytes before materialization; new model entities need explicit inventory and SQL-permission coverage.

This component cannot report an effective or released hold. A valid older database can still lose its entire control tail, so external immutable witness/restore reconciliation and fencing of every mutation, late write and destructive action remain mandatory. Multiple holds retain independent blocking state. No original retention clock, participant session, ordinary source protection or runtime authority changes. Freeze/item/control journal migration and local tests do not authorize hosted schema, grants, protection or provisioning.

The frozen-plan codec and durable control journal are implemented and unregistered. They own bounded capture/ciphertext copies before awaiting SQL, preserve exact SQL/manifest bytes and the complete deterministic item plan, bind placement to authenticated request evidence, and check canonical content on read. Plan replay returns the original persisted ciphertext. Item recording invokes the verified archive writer under current-state authorization; it cannot accept a caller-supplied provider fact as a receipt. Exact receipt replay verifies actual retained bytes and protection again, and restart/lost SQL commit recovers the same provider version without reupload or clock renewal.

Control persistence design: one append-only private control table stores a maximum 41 MiB already-protected plan payload separately from small encrypted event metadata. Each row binds record/hold/plan/event IDs, sequence, UTC time, policy/plan/item digests, payload digest and prior chain hash. Bound the whole private control journal to 16,384 events and 128 MiB before materializing it. Plan replay returns the original exact protected payload. Item recording invokes the verified archive writer under fresh current-state authorization; callers cannot submit arbitrary provider-fact DTOs as receipts. Receipt readback verifies planned path/hash/length/version/ETag bindings. A versioned SQL snapshot authenticates its exact captured control prefix separately and fresh authorization requires extension. The journal remains preservation-pending and unregistered; external witness and lifecycle fencing are still required.

SQL inventory v2 keeps all existing business/request rows in its content fingerprint, with only separately authenticated control publication outside that fingerprint. It authenticates a captured control sequence/hash and verifies extension against the current complete control history before worker authorization. Explicit control-column coverage and model coverage reject silent evidence omissions. Model 30 adds only the private table, indexes, foreign keys and bounds; existing runtime/worker roles receive no access. The ciphertext column has its own size constraint and is explicitly excluded from the generic 32-byte digest convention.

All 185 focused cases pass warning-free, including real disposable SQL schema/permissions, concurrent exact/independent plans, restart/replay, rollback/lost commits, deleted prefixes and recomputed-hash tampering, caller-buffer mutation, provider refusal/corruption/protection loss/expiry, exact receipt recovery, stale business and pending release. Release configuration matches the migration. Source inventory also uses actual loopback Azurite; archive protection uses intercepted SDK transport, not live Azure immutability. A receipt is historical verified component evidence: complete historical references, an authenticated complete-bundle/lifecycle receipt, external immutable witness/restore reconciliation, all mutation/deletion/late-write boundaries and actual effective/released multi-hold states remain mandatory before activation or merging this story.

## Typed historical snapshot references

The typed reference component authenticates bounded canonical contact-retirement signer/field snapshots, accepted Finish field snapshots and pre-publication envelope snapshots against their exact record/party and saved digest/recipe. Contact revision metadata also binds its retired payload and historical source document. Every nested historical source/final/mark reference must match exact inventoried bytes; a current signer or field row does not replace old evidence. Unknown, partial, foreign or malformed nested evidence fails. A streaming preflight bounds field arrays before allocating entity instances. This step does not cover all opaque audit/protected-outbox references and does not supply complete-bundle or effective-hold authority.

## Protected verification and decline history

Historical sender-verification and signer-declined mail is authenticated during both capture and manifest replay. Canonical protected wrappers and typed plaintext reject unknown or duplicate fields that might conceal future references. Verification binds the saved sender and canonical random-token encoding; an issued token must match its exact identifier, purpose, mailbox, parent and digest. Never-submitted queued work may legitimately precede token issuance. Reading expired or used token evidence creates no token and changes no access deadline.

Decline mail binds its exact canonical `declined` audit entry, saved audit hash, signer identity/name/mailbox, normalized reason, frozen title and disclosure digest. The audit's historical document digest must have matching bytes at an owned normalized document path in the inventory; a newer current PDF cannot replace those bytes. Capture and replay reject a missing or ambiguous audit, foreign party, changed reason or omitted historical source even when an attacker recomputes unkeyed hashes. This authenticates that notification's reference, not the entire audit chain or registry.

Completion/void notifications, the remaining audit schemas, complete-bundle and lifecycle receipts, external witnesses and whole-database restore reconciliation, mutation/deletion fencing and effective/released states are still required. The helpers remain internal and unregistered; no provider, schema, route, privilege or visible workflow changes are included.

## Protected void notification history

Void notification capture and manifest replay authenticate the existing typed payload and canonical protected JSON. They bind the global void audit ID/hash and predecessor, exact original affirmative statement, normalized reason and UTC transition, original sent/disclosure digests and exact current normalized source. A processed checkpoint chain binds a later copy; an accepted but unprocessed Finish remains a separate retained reference and cannot become the void's source. These checks do not replace complete Finish/audit graph validation.

The payload binds the post-void envelope revision, distinct from the pre-void reviewed revision. Roster and member digests preserve the runtime sender/signers/recipients and canonical queue evidence. SQL Server uniqueidentifier ordering is reproduced explicitly with SqlGuid for recipient rows; ordinary Guid ordering would change the saved roster digest. Completion-only recipients affect that digest but receive no void notice. Destination deduplication preserves a single sender notice when the sender also signs.

Historical reads apply no live session/retention clock and issue no capability or notification. Complete opaque audit/recipe reference coverage, complete-bundle/lifecycle receipts, external restore witnesses, every mutation/deletion fence and effective/exact independently released hold states remain required. The backend remains private and unregistered.

## Complete chain structure and owned notification registry

Object capture and authenticated manifest replay check the entire bounded retained audit chain, including the operational tail after an enrollment or completion anchor. Global audit IDs must be positive and unique; per-record sequence must begin at one without gaps or duplicates. SQL export order and gaps in global database identities are immaterial. Each event binds its parent, exact predecessor and canonical hash, elapsed UTC time and bounded defined actor metadata. Bounded JSON must be an object and contain no duplicate properties at any nesting level. Producer whitespace, property order and numeric lexemes remain unchanged; hashes use the existing audit algorithm.

The owned-mail registry permits only the seven templates with historical reference codecs, then runs those codecs. Unknown future templates, global lookup/simulator mail misclassified as record-owned, foreign/null owners and duplicate mail IDs fail. Global mail remains excluded by the SQL inventory rather than being imported into a record bundle.

These checks verify chain structure and notification references. They do not yet establish each event's business actor role or the complete typed audit/recipe/object graph. Those codecs, complete-bundle/lifecycle receipts, external whole-database rollback witnesses, every mutation/deletion fence and exact independently released hold states remain required. The internal backend remains unregistered and grants no participant or operator authority.

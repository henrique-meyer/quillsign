# Restricted pilot secret cleanup

This source-only component schedules deletion of the encrypted restricted-pilot mailbox manifest after seven days. It is explicitly composed, has no endpoint and does not enable application email or timestamp calls. Ordinary startup remains unchanged.

`AddEmailPilotSecretCleanup()` registers scoped `EmailPilotSecretJobs`, `EmailPilotSecretCleanup` and the lazy cleanup factory consumed by `DemoPurgeHandler`. The operator coordinator must call `PrepareAsync(EmailPilotManifest, CancellationToken)` before admitting an envelope. Its `EmailPilotSecretPreparation` result reports the deterministic `WorkId`, whether an existing item was recovered, and whether the committed wake was published. A missing publication acknowledgement leaves the durable hint available for existing storage recovery.

Preparation checks the supplied manifest digest against the immutable SQL run tombstone. It records only the random run ID, creation time, seven-day deletion time and manifest digest in a canonical reserved `WorkKind.Purge` payload, with no envelope ID. No contact value, raw capability or protected manifest enters work or hint storage. Run locking precedes work-row locking, matching the accounting ledger. An initial job is due exactly seven days after creation; subsequent owned worker retries can advance its scheduling time without changing that payload or resetting attempts. Recovery does not extend the run or secret lifetime. The hint is saved before SQL commit and the wake is published afterward.

The lazy purge pre-route validates the exact owned work lease, attempt, kind, deterministic identity, payload, persisted run and due time. It then executes the existing `RemoveExpiredEmailPilotSecrets` procedure inside its transaction, checks that the private secret is absent, and rechecks lease/time before commit. The procedure uses database UTC and independently requires the original seven-day deadline. Moving an application clock forward cannot erase a new secret. A lost acknowledgement is safely retried: an already absent secret succeeds while accounting reservations, enrollment identifiers and run tombstones remain. A stale lease, corrupted scope or unavailable dependency is retried without deleting other data.

Cleanup intentionally does not depend on the current pilot enable flag, configured run ID, contact key ring, document/blob access, email transport or timestamp authority. An expired or disabled run must still lose its secret on schedule. The ordinary runtime identity can prepare work but cannot execute the cleanup procedure or delete private rows. `database grant-email-pilot-retention` exposes the existing checked worker-only grant as an explicit operator command; installing this source does not run that command or change permissions.

Existing work messages and durable hint recovery provide scheduling. There is no new recurring SQL poll, table, work-kind enum, migration, cleanup procedure, cloud resource or provider usage. Hosted activation and its approved permission/release steps remain separate.

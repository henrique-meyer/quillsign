# Internal timestamped platform PDF seals

QUILS-40 turns the [sealing feasibility findings](pdf-seal-feasibility.md) into an internal, bounded operation. `PlatformPdfSeal.SealAsync` consumes a prepared PDF and its expected SHA-256 and returns verified sealed bytes, source/output hashes, certificate identity and distinct server-seal/TSA times. It does not authorize signing, publish blobs, mark an envelope completed or send mail. Completion pages and their durable publication remain subsequent work.

## Certificate and source boundaries

The operation copies and hashes its bounded input, applies existing unsigned/unencrypted PDF validation and rejects unflattened form fields. It preserves source bytes and page geometry; the output hash identifies the newly serialized sealed file. No final-file hash is written recursively into that same file.

`ISealCertificateProvider` supplies an operation-owned lease. QUILS-41 selects configured PFX, Key Vault or persistent demo material; each uses ephemeral key handles, bounded PKCS#12 loading and default KDF limits. Key material is disposed and temporary private byte buffers are cleared. The engine checks validity, signing key usage, non-CA status, RSA 2048–8192 or supported ECDSA curves. If EKU is present, it must include the [document-signing purpose defined by RFC 9336](https://www.rfc-editor.org/rfc/rfc9336.html).

Missing or unusable configured material fails closed. The engine never substitutes an ephemeral production certificate. A platform certificate establishes the seal's cryptographic identity; it does not identify or express intent for individual human signers.

## Provider selection and persistence

`Seal__Provider` defaults to `Auto`. Any PFX path/password selects PFX; any Key Vault URI/name/identity selects Key Vault. Configuring both requires an explicit choice. Partial configuration selects its provider and fails validation rather than falling back. Explicit values are `Pfx`, `KeyVault` and `SelfSigned`. No exception path tries a second provider. Registration and resolving the engine perform no storage, certificate or network access; provider acquisition happens only for an explicit seal operation after the engine validates the source and TSA configuration.

PFX uses `Seal__Pfx__Path` (absolute) and `Seal__Pfx__Password`. Key Vault uses `Seal__KeyVault__Uri` and `Seal__KeyVault__CertificateName`, with system-assigned managed identity by default or the configured `Seal__KeyVault__ManagedIdentityClientId`. The adapter currently accepts commercial Azure vault hostnames over HTTPS. It reads the selected latest certificate and only its exact backing secret version, validates scope/enabled/validity metadata, requires `application/x-pkcs12`, and matches the loaded private certificate to the selected public DER. This requires an exportable certificate and read permissions for that certificate and secret; a non-exportable signing-key API is not implemented. Managed identity never falls back to developer CLI credentials. SDK calls are bounded, cancellable, do not follow redirects, and disable SDK request/content logging. Actual vault values and permissions remain operator-managed private configuration; this code provisions nothing.

With neither external provider configured, `Auto` uses a persistent RSA-3072 self-signed **QuillSign Demo Seal**, including the document-signing EKU. Its PKCS#12 exists only in memory before Data Protection encryption. The encrypted object is created once under the existing private `keys` container at `Seal__SelfSigned__BlobName` (default `demo-seal-v1.dp`). Conditional creation and rereading select one winner across concurrent instances and recover an uncertain create response. The provider does not create hosted containers; local Azurite alone may create its private test container. Missing hosted storage, corruption, lost protection keys, expired or unsuitable saved material all stop sealing without automatic overwrite or rotation. `Seal__SelfSigned__ValidityDays` defaults to 365, bounded to 7–3650 days for initial generation only.

The demo object and the Data Protection key ring must survive application restarts and document retention cleanup. Keep the same application discriminator and retain the wrapping keys needed to decrypt older material. Hosted Data Protection already uses its separately configured Key Vault wrapping key. Back up these protected objects and wrapping-key access together; do not put private keys or vault values in Git. Intentional rotation requires an operator-managed change of certificate/configuration or a new protected object name after planning retention of the old identity; the application does not delete or replace it. A self-signed identity provides tamper evidence with its recorded fingerprint, not public CA/Adobe trust, individual signer identity or a qualified signature.

Provider tests reconstruct instances, race conditional creation against Azurite, reject tampering/wrong protection keys/expired material, and verify actual retained-identity PDF seals against a generated loopback TSA. Key Vault tests run the real SDK JSON/pipeline through fake transports and credentials, including exact secret version, metadata/binding failures, byte limits and cancellation. They contact no vault or identity endpoint.

## Timestamp protocol and trust

`Seal__TsaUrl` has no default. Production requires HTTPS without credentials, query strings, fragments or redirects. Development additionally permits loopback HTTP for fixtures. The transport sends only a SHA-256 imprint of the CMS signature and a fresh 128-bit nonce; it sends no PDF, signer values or document title. Timeout, response length and content type are bounded. Failed, malformed, mismatched, stale/future or untrusted responses produce no returned seal.

Response validation checks the request nonce/imprint, token signature and signing-certificate binding, critical sole timestamping EKU, validity at TSA time, supported key/digest and a chain to OS trust roots or explicitly supplied private roots. Configure custom roots using `Seal__TsaTrustedRootPaths__0`, etc. Certificate downloads and revocation network lookups are disabled. These checks follow [RFC 3161's response-binding requirements](https://www.rfc-editor.org/rfc/rfc3161.html); .NET and BouncyCastle independently verify the token signature and binding. The returned timestamp policy is the authority's token policy, not an operator policy invented by QuillSign.

This slice does **not** check or preserve revocation evidence, supply LTV validation, establish Adobe trust, certify a qualified timestamp or claim PAdES/AdES/QES conformance. Production TSA interoperability and external viewer validation remain integration gates. Synthetic fixture roots are passed privately to the operation and never installed into system trust stores.

## Complete output verification

PDFsharp remains pinned to MIT-licensed 6.2.4. Its custom signer produces detached CMS with SHA-256, signed signing-time and `SigningCertificateV2`, and a verified RFC 3161 signature timestamp. Reservation sizing signs a small local CMS using the operation's actual certificate and chain, then adds the configured maximum timestamp-response size, 1 KiB for ASN.1/variable signature growth and rounding to 4 KiB. `Seal:SignatureCapacityBytes` remains the upper bound; an actual result exceeding the reserved space fails closed. Sizing never contacts the TSA or consumes a timestamp allowance; each successful operation makes one timestamp request. This reduces unused hex padding in new PDFs without altering existing published files. Previously sealed files with a larger reservation remain subject to the same verification checks. Signers are operation-local and a semaphore bounds concurrent sealing memory.

The engine parses its output through PDFsharp's object model rather than copying the spike's regex parser. It requires one signature field/dictionary, `/adbe.pkcs7.detached`, a complete four-number ByteRange with only the exact hex Contents gap, zero padding and no trailing uncovered bytes. It verifies the detached digest/signature in .NET and BouncyCastle, the exact acquired certificate, signed certificate/time attributes and the embedded timestamp. It also compares final page geometry before returning any bytes. This is a verifier for the engine's complete single-seal output, not a public untrusted-upload or incremental-revision verifier.

## Reproduce

Run `pwsh -File scripts/dev/Test-PlatformPdfSeal.ps1`. It needs .NET 10, Node.js for the existing asset build and OpenSSL; it needs no SQL, cloud credentials, public TSA or live email. Tests generate local ephemeral keys and a loopback authority. The helper independently verifies production CMS/timestamp output with OpenSSL and rejects changed signed bytes/imprints. `cms -noverify` verifies content/signature but deliberately does not assert public trust in the synthetic platform certificate. Timestamp verification trusts only the supplied synthetic root. Windows and Linux CI run the same helper.

Evidence stays under ignored `artifacts/platform-seal/`: source/sealed PDFs, detached CMS, signed bytes, timestamp, signature value and the public TSA root. Private keys are not exported there. Render both PDFs with Poppler for visual comparison; sealing adds no visible mark or new page. Actual TSA/certificate configuration remains empty in examples, and registration performs no certificate, network or database work at startup.
## Shared timestamp request coordination

FreeTSA permits at most one timestamp request per second per public source IP and offers no SLA ([provider policy](https://www.freetsa.org/freetsa.html)). QUILS-61 adds optional shared coordination for the existing RFC3161 client. Requests to FreeTSA require it and explicit trusted CA paths; other configured providers retain their existing behavior unless coordination is enabled.

Set `Seal__TimestampCoordination__Enabled=true`, retain `Seal__TimestampCoordination__MinimumIntervalMilliseconds=1000` or a larger value up to 10000, and configure `Seal__TimestampCoordination__AcquireTimeoutSeconds` from 1 to 60 (default 30). Coordinated requests require `Seal__TsaTimeoutSeconds` at most 30. Configure the verified public CA through `Seal__TsaTrustedRootPaths__0` and the provider URL through `Seal__TsaUrl`. No actual provider, root file or runtime setting is enabled by this change.

The default adapter uses the existing Blob service and `keys` container. All workers sharing egress must use the same storage and provider scope. An empty blob with a hashed origin name holds an exclusive 60-second lease; FreeTSA host aliases share the same scope. It contains no document bytes, digest, nonce, certificate, private key or clock metadata. Only local Azurite creates containers; hosted infrastructure is provisioned separately. There is no process-only or SQL fallback. Self-hosters can use the existing shared Azure storage adapter or explicitly register an `ITimestampRequestCoordinator` that provides equivalent deployment-wide protection; a process-local semaphore is insufficient for multiple workers or deployments sharing an IP.

Ownership is renewed immediately before HTTP submission. A conservative lease-bound cancellation budget and the bounded HTTP timeout stop work before the lease can expire. The lease remains held through response verification and at least one second of cooldown after every attempt, including failed or cancelled requests. Cleanup does not skip that cooldown when the caller cancels. A crashed process leaves the finite lease to expire; it never breaks another worker's lease to make progress. Storage/ownership/contending-wait failures return a recoverable seal error before any uncoordinated HTTP request. If releasing a lease fails after cooldown, the remaining lease expires naturally. See [Azure Blob lease semantics](https://learn.microsoft.com/en-us/azure/storage/blobs/concurrency-manage#pessimistic-concurrency-for-blobs).

Both final PDF seals use the same coordinator. No timestamp, nonce, imprint, CMS signature, certificate-purpose or trust-chain check is relaxed. Readonly verification of already sealed bytes does not acquire a coordinator, access SQL/storage or contact the TSA. Hosted CA/configuration rollout and end-to-end validation remain necessary; the public provider can still be unavailable and delay completion.
